# 용어집 정리 절차

세 층이 있다. 어디에 넣을지 먼저 정한다.

| 층 | 파일 | 누가 바꾸나 | 적용 범위 |
|---|---|---|---|
| 공용 도메인 | 플러그인 `glossaries/<언어>/<도메인>.md` | 공용 저장소 PR + 도메인 검토자 | 문서·주석·보고 전부 |
| 프로젝트 | `docs/glossary.md` (설정으로 변경 가능) | 이 저장소 PR | 문서·주석·보고 전부 |
| 개인 | `~/.claude/glossary/personal.md` | 본인 자유 | 보고·설명·질문에만 |

표 형식은 `references/glossary-format.md` 를 따른다. 세 층이 같은 열을 쓰므로 검사 스크립트 하나가 다 읽는다.

**언어** — 플러그인 설정 `language`(ko|ja)가 공용 도메인 폴더(`glossaries/<언어>/`)와 사용자에게 보여 주는 말을 정한다.
후보 표·보고·용어집 행은 그 언어로 쓴다. 후보 표 양식은 ko 면 `references/candidates-template.md`,
ja 면 `references/candidates-template.ja.md` 다. 공용 용어를 바꾸면 다른 언어판의 같은 행도 맞추라고 안내한다.

## 정리 (`/glossary 정리`, 또는 PR 생성 전)

1. **추출** — 현재 브랜치의 기본 브랜치 대비 변경(`git diff <base>...HEAD`), 작성한 문서, 이 대화에서 보고한 문장에서
   새로 만들었거나 이 프로젝트에서 쓰지 않던 용어를 뽑는다. 일반 프로그래밍 용어와 이미 용어집에 있는 것은 제외한다.
2. **후보 표** — 저장소 밖 임시 파일(스크래치패드)에 설정 언어의 후보 표 양식으로 쓴다.
   같은 개념이 공용 도메인에 이미 있으면 "공용 용어 재사용"으로 표시하고 새 이름을 만들지 않는다.
3. **확인 대기** — 파일 경로를 알려 주고 사용자가 "확정" 열을 채울 때까지 기다린다. 확정 전에는 아무것도 바꾸지 않는다.
4. **반영**
   - 문서·주석·화면 문구·보고 문구는 바로 바꾼다.
   - 코드 식별자·API 필드·DB 컬럼·`data-testid` 는 사용처를 확인하고 사용자가 지정한 것만 바꾼다.
   - 바뀐 용어의 옛말은 "쓰지 않을 말" 열로 옮긴다. 지우지 않는다.
5. **용어집 갱신** — 프로젝트 층이면 `docs/glossary.md` 표와 변경 이력에 추가해 **같은 PR 에 커밋**한다.
   공용 층 후보면 공용 저장소에 PR 을 내라고 안내하고, 그 전까지는 프로젝트 층에 넣는다.

## 검사 (`/glossary 검사`)

```bash
"${CLAUDE_PLUGIN_ROOT}/scripts/lint-glossary.sh" [경로...]
```

공용·프로젝트 용어집의 "쓰지 않을 말"이 `docs/` (또는 지정 경로)의 Markdown 에 나오면 파일:줄을 출력하고 종료 코드 1 을 낸다.
개인 별칭이 문서에 나오면 그것도 쓰지 않을 말로 다룬다. PR 생성 전에 한 번 돌린다.

## 개인 별칭 (`/glossary 개인`)

사용자가 "나는 X 를 Y 라고 불러" 하면 `~/.claude/glossary/personal.md` 의 표에 `내 말 | 대응 용어 | 메모` 한 줄을 더한다.
파일이 없으면 `templates/<언어>/personal-glossary.md` 를 복사해 만든다. 개인 별칭은 **새 개념을 정의하지 않는다**. 대응 용어는
공용·프로젝트 용어집에 있는 것이어야 하며, 없으면 먼저 "정리" 절차로 용어를 만든다.

## 승격

- 개인 별칭을 두 사람 이상이 쓰면 프로젝트 후보로 올린다.
- 여러 프로젝트에서 같은 용어가 확정되면 공용 도메인 후보로 올린다.

## 하지 않는 것

- 확정 전 반영, 옛 용어 삭제, 개인 별칭을 문서·커밋·PR 에 쓰기, 개인정보·비밀값을 용어집에 넣기.
